# WebView2 のメモリ使用量を抑える（検討メモ、2026-10-25）

HANDOFF.md §10「最小化中の省メモリと計測」から参照する。議論用の版は Claude Docs の「WebView2 のメモリ使用量を抑える（検討メモ）」（https://claude.ai/artifact/3rGq54wxVn8QnuQiXzqzdk）。

## 1. 背景

- 利用者の実感値（2026-10-25）: VB.NET だけの WinForms アプリは 100MB 未満、WebView2 のアプリは 100MB 超（タスク マネージャー）
- WebView2 はアプリの exe とは別に Chromium のプロセス（ブラウザ・GPU・ユーティリティ・レンダラー・crashpad）を起動する。差の大半はこの固定費で、設定では消せない
- 固定費（ブラウザ・GPU・ユーティリティ）は **ユーザーデータフォルダ（UDF）と環境オプションの組ごとに 1 組**。同じ `CoreWebView2Environment` から作った WebView2 は共有する。伸びるのはレンダラーの中身（DOM・JS ヒープ・画像）で、一覧の行数や開いている窓の数で増える
- 狙いは 3 つ: **共有する**（窓やアプリを増やしても固定費を増やさない）/ **伸ばさない**（大量の行・窓・データ）/ **休ませる**（最小化中にメモリを返させる）

## 2. 案と状態

| 案 | 効く場面 | 状態 |
|---|---|---|
| A. 複数アプリで UDF を共有し、データは `CoreWebView2ControllerOptions.ProfileName` で分ける | 母艦から複数の WebView2 アプリを同時に開く | 未着手。同時に開く本数を利用者に確認中 |
| B. 画面を別 exe にせず、同じ exe の窓で開く | 同じ業務の画面を並べる | 済（サブウィンドウ A。同じ Environment と opener 関係なので固定費は共有） |
| C. 最小化中は IsVisible=False + `MemoryUsageTargetLevel=Low` | 最小化して裏に置く時間が長い | **実装（`MinimizedMemorySaver`、opt-in、本体で有効）。Windows で未確認** |
| D. 最小化中は `TrySuspendAsync` | C と同じで、裏で何も動かなくてよい | 見送り（C を測ってから） |
| E. 一覧の仮想化（見えている行だけ描く） | 数千〜数万行の一覧 | 大きな一覧の画面が出たときに見本を入れる |
| F. 大きな応答の zod 検証を開発時だけにできるオプション | 数万行を一度に受け取る | 見送り（まずページング。§10「大きな配列」） |
| G. VB 側の応答を `JToken` の木を経ずに直接書く | 大きな応答 | 見送り（効く場面が狭い） |
| H. ブラウザ引数 `--js-flags=--scavenger_max_new_space_capacity_mb=8` | JS で大量に物を作る画面 | 見送り（効果は小さい見込み。A と組むなら全アプリで揃える） |
| 入れない: `--disable-gpu`、`--single-process` など | — | Microsoft は GPU を切ることを勧めていない。single-process は不安定 |

## 3. 案ごとの要点

- **A**: 全アプリで環境オプション（ブラウザ引数・言語など）を完全に揃えないと、後から起動したアプリの初期化が失敗する。全アプリが同じ `https://app.local` なので、プロファイルを分けないとキャッシュ・IndexedDB を共有してしまう。`BridgeWindows` の子ウィンドウも同じプロファイルで作らないと `e.NewWindow` が成立しない（コントローラーオプションを受け取る形に変える）。最後のアプリを閉じるまでブラウザプロセスが残り、ブラウザプロセスが落ちると全アプリの画面が落ちる（`ProcessFailed` で再読込が要る）。1 本が固まると別アプリの入力も詰まるという報告がある（WebView2Feedback #2707、公式ではない）
- **B（1 つの exe をランチャーにして窓で画面を増やす）**: exe を 1 本足すごとに WebView2 の固定費と .NET のプロセスがもう 1 組増えるので、メモリだけなら 1 つの exe の窓の方が少ない（2026-10-25 に利用者から質問）。代わりに、全部の窓が 1 本の UI スレッド（VB の Dispatcher もここで動く）と 1 つのレンダラーを共有するので、1 画面の重い処理や固まり・落ちるのが全部の窓に及ぶ。業務ごとの契約・実装・配布の版も 1 つにまとまる。勧める分け方は「同じ業務の画面はサブウィンドウ、別の業務は別 exe」。別 exe のまま WebView2 の分を減らすのが A（.NET の分は残る）
- **C / D**: WinForms の WebView2 は Form が最小化されても自分では何もしない（Microsoft は最小化・復元で Controller の `IsVisible` を切り替えるよう勧めている）。Low はスクリプトも通信も止めないので、ブリッジ・通知・待ち中の呼び出しに影響しない。`TrySuspendAsync` は `IsVisible=False` が前提で、スクリプト・タイマーも止まり、表示に戻れば自動で再開する。TrySuspend は Low も自動で掛けるので C と混ぜない。止まっている間の `PostWebMessageAsJson`（応答・通知）が自動再開させるのか溜まるのかは未確認
- **E**: 10 列の表は 1 行で数十の DOM ノードになり、数万行をそのまま描くとレンダラーが数百 MB に届きうる（概算）
- **F**: `createClient` は受信した結果を zod で `safeParse` して新しいオブジェクトを作るので、大きな応答では同じデータが一時的に 2 組並ぶ
- **G**: `JsonRpc` は結果を `JToken.FromObject` で木にしてから `ToString` している。`JsonTextWriter` に直接書けば木が要らない

## 4. 測り方

`scripts/measure-memory.ps1`（Windows PowerShell 5.1 / PowerShell 7）が、exe とその子孫のプロセスを種類別（exe / browser / gpu-process / utility / renderer / crashpad-handler）に並べ、Private（コミット量）と WorkingSet（今 RAM にある量）を出し、exe だけ / WebView2 だけ / 合計を出す。

```powershell
.\scripts\measure-memory.ps1                       # 本体（WebView2Bridge.Host）
.\scripts\measure-memory.ps1 -Name MyApp.Host      # 雛形から作ったアプリ、純粋な WinForms のアプリも同じ
.\scripts\measure-memory.ps1 -AllWebView2          # UDF を共有したとき（WebView2 は最初に起動したアプリの子になる）
```

- タスク マネージャーの「プロセス」タブでアプリの行を折りたたんで見た「メモリ」は、WebView2 の分も入った合計（プライベート ワーキング セット）。「詳細」タブの exe の行だけだと WebView2 の分は入っていない
- Release ビルドで、DevTools を閉じて測る。各場面で 30 秒ほど待ってから 3 回測る
- 場面: (1) 起動直後 (2) 検索して一覧を出した後 (3) サブウィンドウを左右に 2 枚開いた後（レンダラーが増えないか）(4) 最小化して 1 分後（C の効果。主に WorkingSet に出る）(5) アプリを 2 本同時に起動（A を考えるとき）(6) exe 2 本と、exe 1 本 + サブウィンドウ 1 枚の比較（B。合計で比べる）
